# 编写技术方案文档

产出可直接用于跨角色评审的技术方案。文档必须同时满足：

1. 业务规则、流程、数据和接口设计正确。
2. 产品、测试、前端及其他研发能够读懂。
3. 上线治理内容完整，包括影响范围、容量、历史数据、兼容性、SOP 和回滚。

## 基本原则

### 先调查，再设计

针对现有项目，编写前必须核对：

- 需求真源和最终业务规则。
- 功能所在的真实系统和现有模块。
- 可以复用的接口、数据模型、配置、定时任务和基础能力。
- 实际上下游系统及调用方向。
- 真实组织角色和上线职责。

不能仅根据目录名、旧文档或常见做法推断现状。存在多份需求材料时，应明确最终真源，避免从聊天记录重新推导已经固化的规则。

### 业务概念先于代码名称

- 先定义业务概念、关系和状态，再描述流程和实现。
- 包名、类名、接口路径、字段名、枚举名只有在代码库已有依据或设计已明确时才能写入。
- 尚未确定的代码结构使用业务概念描述，不得为了显得完整而虚构名称。
- 代码标识首次出现时解释其业务含义，不能只写字段或枚举让读者自行推断。

### 面向读者，不写写作过程

成稿中禁止出现以下内容：

- “本文面向……”“流程图只描述……”“下文将……”“为了便于读者理解……”等写作过程或作者说明。
- “回答三个问题”“先来看一下”等口语化引导语。
- 未定义的简称、行话或抽象占位词。
- 对技能、模板、提示词或写作选择的解释。

直接陈述业务事实、设计和约束。

### 不猜测

以下内容没有可靠依据时，不得编造：

- QPS、数据量、存储增量、批次大小、等待时间等数值。
- 系统名、接口名、表名、字段名和错误码。
- 运维、DBA、数据团队等组织角色。
- 数据库、中间件或部署环境的实际状态。

缺少数据时应写“待确认”，或给出计算方法、压测方法和确认时点。组织资料明确时使用真实角色；没有角色依据时，数据库、配置和上线操作默认由研发负责。

## 编写流程

### 1. 确认需求真源

读取 PRD、规格、票据、领域词汇表和相关沟通结论，提取：

- 目标、范围和范围外。
- 用户、权限和数据隔离。
- 核心规则、异常规则和幂等规则。
- 性能指标、历史数据和兼容性要求。
- 验收场景。

发现材料矛盾时先确认，不带着冲突继续设计。用户在当前会话中明确修正的规则优先于旧 PRD、旧规格和旧文档；修正后应同步检查所有受影响章节。

### 2. 调查现有实现

至少确认：

- 功能应由哪个现有系统负责。
- 管理入口、后端业务、配置、存储和外部能力分别在哪里。
- 现有能力如何调用，是否存在失败、重试或事务限制。
- 真实字段、状态、索引、权限和角色。

调查结果只用于支撑设计，不要把代码搜索过程写入成稿。

对“现有能力”“复用现有方式”“现有表已支持”等陈述，必须能对应到已读取的代码或配置。没有完成核对时，不得用“现有”表述。

### 3. 定义核心业务模型

当功能涉及以下任一情况时，应在流程设计前增加“核心业务模型”：

- 多个容易混淆的业务对象。
- 当前与历史、状态流转、累计与归档。
- 主记录与多条明细。
- 自动任务与人工操作共用规则。
- 跨页面或跨系统使用同一身份。

模型定义应说明：

| 内容 | 要求 |
|---|---|
| 名称 | 使用业务人员能够理解的名称 |
| 含义 | 一条数据或一个概念代表什么 |
| 产生时机 | 何时创建 |
| 变化方式 | 如何累计、修改、归档或失效 |
| 关系 | 一对一、一对多或分组关系 |

模型不是数据库表的同义词。业务模型确定后，再决定如何落表。

只有同时满足以下条件之一，才能作为独立业务模型：

- 有独立身份，需要被单独查询或引用。
- 有独立生命周期或状态变化。
- 包含自己的业务规则和行为。
- 与其他对象存在明确的一对多、多对多或归档关系。

仅仅是一组字段时，不应提升为独立模型。例如“违规发生时保存的车主姓名、手机号和部门”如果直接存放在违规明细中，就应描述为违规明细字段，而不是单独的“车主快照模型”。

未达到独立模型条件的字段组，也不要作为一行放入核心业务模型表；应在所属模型的含义或字段说明中直接描述。

简单功能没有独立模型时，可以省略该可选章节。

### 4. 描述总体架构

总体架构只回答：

- 功能位于现有系统的什么位置。
- 哪些系统或现有模块需要修改。
- 哪些现有能力被复用。
- 数据和外部调用流向哪里。

不要在总体架构中预先设计包结构、类名或内部方法。除非方案本身就是模块重构，否则架构图不展开代码内部层次。

### 5. 描述业务流程

- 流程图使用已经定义的业务概念，不使用未解释的类名、字段或枚举。
- 一张图表达一个明确主题。
- 正常流程和关键异常流程都要覆盖。
- 不得根据行业惯例补充需求中没有的业务规则。例如材料只写“车辆通行记录”时，不能自行增加“边界记录”“内部道闸”或“场中场”规则。
- 状态图只表达同一种对象的状态变化，不能把车辆状态、周期状态和任务状态混在一张图中。
- 循环返回时要明确是复用原节点、创建新对象还是重新开始，避免看起来像历史数据被重新启用。

**REQUIRED SUB-SKILL:** 使用 `mermaid-drawing` 绘制所有图。

### 6. 完成功能与数据设计

功能设计按业务依赖顺序展开，每个功能说明：

- 改动原因。
- 改动前的能力或缺口。
- 改动后的业务行为。
- 正常、失败、重复和并发场景。
- 与现有能力的调用关系。

数据库章节按以下顺序编写：

1. 业务模型如何落表。
2. 为什么拆成这些表。
3. 表之间如何关联。
4. 关键字段解决什么问题。
5. 唯一约束、并发、幂等、逻辑删除和索引设计。
6. 完整 DDL。

ER 图中的实体名必须与 DDL 实际表名完全一致。DDL 字段、枚举、接口字段和正文术语必须互相对应。

数据设计遵循最小必要原则：

- 不能因为业务模型有多个概念就机械地“一模型一张表”。
- 不能为了范式化而新增没有独立查询、生命周期或数量扩展需求的关联表。
- 新增表必须说明不放入现有表或父表的原因。
- 声称“沿用现有存储方式”前必须核对真实表结构或代码。
- 如果存在两种合理落表方式，应比较一致性、查询成本和变更成本后明确选择。
- ER 图只展示已经选定的物理表，不展示候选关系、逻辑占位表或尚未确定的表名。
- 物理表名或落表方式尚未确定时，数据库章节应明确“待代码库和表结构确认”，不得为了完整而绘制临时 ER 图。

### 7. 补齐生产治理

必须覆盖：

- 影响范围及测试范围。
- 性能和容量评估。
- 线上历史数据处理。
- 上下游和历史兼容。
- 上线操作 SOP。
- 上线验证。
- 回滚步骤和数据处理。

不涉及的必选章节必须保留标题，并用一句话说明原因。禁止通过长清单反复说明“不需要做什么”。

### 8. 通篇一致性检查

交付前逐项检查：

- 术语是否统一，概念是否首次出现即定义。
- 架构图是否只展示真实系统和正确调用方向。
- 核心模型、流程、功能设计是否表达同一套业务规则。
- 每个独立业务模型是否满足身份、生命周期、规则或关系中的至少一项，而不是普通字段组。
- 核心业务模型表中是否仍出现已声明“不是独立模型”的字段组。
- 状态图是否只描述同一种对象。
- ER 图表名是否与 DDL 完全一致。
- ER 图是否只包含最终选定的物理表，而非候选表或逻辑占位名。
- 正文、DDL、枚举和接口字段是否对应。
- 每张新增表是否必要，是否存在无依据的关联表或冗余汇总表。
- 当前、历史、累计、归档等概念是否前后一致。
- 幂等、并发、外部调用失败和事务边界是否闭合。
- 配置项是否有来源，环境值是否完整。
- 容量数字是否有依据，没有依据时是否给出评估方法。
- SOP 中的负责人是否符合真实组织；没有依据时是否默认研发。
- 回滚方案是否处理已经发生的外部副作用和业务数据。
- 成稿中是否残留写作过程说明、口语化引导语或未定义术语。
- Markdown 表格列数、Mermaid 语法和章节编号是否正确。

以下是推荐骨架。总体架构、流程设计、功能设计及数据库变更的顺序应保持；“核心业务模型”为按复杂度使用的可选章节。其他生产治理章节为必选章节。

## 常见错误

| 错误 | 正确做法 |
|---|---|
| 总体架构直接出现新包名和新类名 | 先说明功能位于哪些现有系统和模块 |
| 流程图使用未定义的字段或枚举 | 使用已经定义的业务概念 |
| 把一轮多条明细画成多个当前周期 | 先定义主记录、周期和明细关系 |
| 把姓名、手机号等字段组包装成独立模型 | 只有具备身份、生命周期、规则或独立关系时才定义模型 |
| 声明字段组不是模型，却仍放进模型表 | 直接写入所属模型的含义或字段说明 |
| 状态图混合多个对象 | 每张状态图只描述一种对象 |
| 数据库章节只有 DDL | 先解释模型、关联、字段和约束 |
| 未调查就声称沿用现有表或存储方式 | 先读取真实代码或配置，没有证据时不得这样表述 |
| 每个业务概念都拆一张表 | 按独立查询、生命周期和数量扩展需求判断是否拆表 |
| 表名未确定就画候选 ER 图 | 先确认最终物理表；未确认时明确待确认并省略 ER 图 |
| 根据行业经验增加需求规则 | 只写需求真源、用户确认和代码调查能够支持的规则 |
| ER 图用概念名，DDL 用另一套表名 | ER 图直接使用实际表名 |
| 写死无来源的 QPS、数据量和批次参数 | 给出测算方法，标记待确认 |
| 默认安排运维或 DBA | 核对真实角色；没有依据时由研发负责 |
| 成稿解释“为什么这样写” | 删除元说明，直接陈述设计 |
| 初稿完成即交付 | 先执行通篇一致性检查 |
