# Requirement Brainstorming

通过自然、协作式对话，把模糊想法整理成双方一致理解的需求。

## 表达规范

文档和回复使用常规书面语：

- 不使用行话、黑话或口语化表达。
- 技术术语可以正常使用。
- 措辞应准确、清楚，避免不必要的复杂表达。

## 核心边界

这个 skill **负责澄清需求并完成下一步交接**：

- 不输出产品或技术设计方案
- 不设计架构、组件、接口或数据流
- 不把设计文档或实施计划作为后续工作的前置条件
- 不指定或强制进入其他工作流
- 用户确认需求摘要后，由用户选择下一步

可视化伴侣仅用于帮助用户表达视觉需求，不用于代替设计方案。

## 工作流程

1. **了解上下文**
   - 如果需求针对现有项目，先查看与需求直接相关的文件和文档。
   - 如果只是讨论新想法，不要求用户先准备项目材料。

2. **判断范围**
   - 识别需求是否包含多个相对独立的目标或子系统。
   - 范围过大时，先帮助用户拆分讨论对象，并一次只聚焦一个部分。

3. **逐个提问**
   - 每次只问一个问题，等待回答后再继续。
   - 能给出清晰选项时优先使用选项；无法预判答案时使用开放问题。
   - 不替用户做关键假设，避免一次提出多个问题。

4. **按需澄清**
   - 目标：为什么要做，解决什么问题。
   - 用户与场景：谁在什么情况下使用。
   - 范围：必须包含什么，明确不包含什么。
   - 规则：角色、权限、状态、数据和业务约束。
   - 优先级：什么是必须项，什么可以以后再做。
   - 限制：时间、兼容性、合规、依赖和已有系统约束。
   - 边界情况：失败、异常、空数据、重复操作和冲突如何理解。
   - 验收标准：满足哪些可观察结果才算完成。

   只询问当前需求真正相关的维度，不机械遍历清单。

5. **持续校准**
   - 简短复述新确认的信息，及时指出矛盾、歧义和未决项。
   - 如果答案改变了前提，回到受影响的问题重新确认。
   - 在关键需求仍不明确时，不提前总结为已完成。

6. **确认需求摘要**
   当目标、范围、约束和验收标准足够清楚时，输出完整摘要：

   - 背景
   - 目标
   - 用户与核心场景
   - 范围内
   - 范围外
   - 业务规则
   - 约束
   - 优先级
   - 边界情况
   - 验收标准
   - 未决问题

   请用户确认摘要。若有修改，继续逐项澄清。

7. **选择下一步**
   用户确认摘要后，告知用户“需求已澄清”，并且只提供以下三个选项：

   1. **直接开始实现**
      - 结束 req-brainstorm 流程。
      - 由当前代理基于已确认需求继续实现。
      - 不要求先产出设计方案、设计文档或实施计划。

   2. **保存完整需求文档**
      - 默认写入 `docs/requirements/YYYY-MM-DD-<topic>.md`。
      - 文档必须完整包含：背景、目标、用户与场景、范围内、范围外、业务规则、约束、优先级、边界情况、验收标准和未决问题。
      - 保存结构化结论，不记录逐字对话。
      - 保存完成后，再次提供这三个选项。

   3. **补充或调整需求**
      - 返回逐个提问流程，只澄清用户希望修改或新增的部分。
      - 更新需求摘要并再次请用户确认。
      - 确认后，再次提供这三个选项。

   用户可以随时要求暂停或结束，也可以暂不选择。

## 可视化伴侣

当 UI 布局、页面结构、流程关系或视觉差异明显更适合通过视觉内容进行选择时，可以提议使用浏览器伴侣。用户同意后，按照 `visual-companion.md` 操作。

- 适合：界面布局、线框图、视觉对比、流程图、空间关系。
- 不适合：范围、规则、优先级、约束等文字问题。
- 不要在对话开始时主动介绍可视化伴侣；仅在确实需要视觉表达时提议使用。

## 完成标准

只有同时满足以下条件，才能告知用户需求已澄清：

- 用户目标明确
- 范围内与范围外明确
- 关键规则和约束明确
- 主要边界情况已讨论
- 验收标准可观察
- 未决问题已列出
- 用户确认需求摘要

确认后必须由用户选择下一步，不能自动进入设计、文档编写或实施。
